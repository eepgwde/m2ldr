# NAME

m2\_ - a *BASH* script that loads and executes functions from another
script.

# SYNOPSIS

`m2_` -h

`m2_` \[options\] \[ `---` \] command \[x-options\|sub-command\]

# DESCRIPTION

`m2_` is a utility script that is used as the target of a link to a
*derivative* script. That derivative script when run will then load a
library file and run functions within it.

The `m2_` script itself provides much of the infrastructure that one
would want a utility script to have.

The derivative script will support the commands that *m2\_* provides.

# ARGUMENTS

*m2\_* and derivative scripts must have the options specified before
command.

If the command specified can take options of its own, like `-X` or
`--long-option` then the `--` needs to be given before the command.

The *m2\_* options are internally represented by shell environment
variables, eg. `-s extra` will set the variable `d_service=extra`. And
similarly for the other options, the variable is named after the option.

Some options have defaults taken from the environment, these are named
above.

Some options engender some post-processing if possible
`d_exec, d_options`, see the MORE VARIABLES section below. The logging
variables `-v, --log,` \--log-dest and \--log-deep are discussed in the
LOGGING section below

Derivative scripts support as many functions as are given in its

## Library Script and Definition Files

If a derivative script is named `script0` then it should have a library
script called `script0.sh`. scripts can also load definition files that
are shell variable definitions. These should be named `script0.def`.

## Library Functions: `d_` and `h_` prefixes

Functions are defined within the library script, for them to accessed
from the command-line as a command, the must be prefixed with `d_`.

For example in `script0.sh`

    d_demo () {
      echo $*
    }

Would allow `$ script0 demo` from the shell. A help function can be
written by prefixing it with `h`, an example might be this for the
`demo` function.

    h_demo () {
      cat >&2 <<EOF

    $prog ${FUNCNAME##h_} [-c]

    Prints the command-line arguments to standard output

    EOF
    }

And it would be invoked like this: `script0 -h demo`

The order is important: the `-h` should appear before the command. The
variable `$prog` is internal to the loader-script and will be the
loader-script without its path. It is derived from `$0`.

There are other function prefix conventions: `e_` and `f_` are used for
internal functions. `s_` is used for functions to be invoked as a part
of stateful operation.

# DEFINITIONS

loader-script

:   is the `m2_` derivative script. In the examples above, it is
    `script0`.

derivative-script

:   is a loader-script but includes it library and definition files.

loader-implementation

:   is the `m2_` loader-script itself. It implements a derivative script
    by using a symbolic from the `m2_` to the loader script.

library-script

:   a shell script file that is loaded by the loader script and has
    functions defined within it prefixed with `d_`.

definitions file

:   a shell script file that is shell variable definitions.

script flavours

:   derivative scripts can have different flavour: user, host and site.
    The flavour determines where the loader-script will search for it
    library and definition files.

site-script

:   is a derivative script that searches the user\'s own directories and
    those of the host. The `user` directory for library and definition
    files is the `etc` directory in the `/home/` directory of the user.

host-script

:   is a derivative script that only searches the host\'s directories:
    `/usr/local/etc`.

user-script

:   is a derivative script that only searches the directory where the
    script is located. It also searches sub-directories named after the
    setting of `d_user` and `d_machine`.

audit-function

:   this is the method `this0` it is described below. It is used to list
    the operational state of the loader-script.

cl-loader

:   is the code-level loader. It is a feature that allows functions from
    another library-script to be loaded by a loader-script. Uses the
    function `d_resolve1`.

name-ref

:   this is a feature of BASH. A shell variable can be passed by
    reference to a function. The variable name is passed as a parameter
    to a function and that function can refer to variable of the caller
    using `local -n __ref`\"\$1\". Then the local variable `__ref` will
    take whatever value the function assigns to it. That value will then
    be accessible on return to the caller by its original name.

# LOGGING

The loader-implementation provides a full featured logging facility.
This can log to a file, or a socket. Sockets can be TCP, TCP6, UDP and
the latter can be used with IPv4 multicast.

The logging information is compliant with `syslog-ng`. The log format is
RFC 3164, [](https://tools.ietf.org/html/rfc3164) .

The destination for logging is specified with the command-line option
`--log-dest=dest`.

The logging command-line options set these two variables that are
usually set in the loader-implementation\'s definition files. These
settings send to multicast and the log level of 2 will make logging
propagate.

    _M_GLOBAL_LOG_DST=mcast://239.255.0.2:17777
    _M_GLOBAL_LOG_LVL=2

These settings are loaded into the loader-script, so it is not enough to
disable logging in the environment. You have to unset these variables in
the files. Use the audit-function to see if they are enabled

    script0 this0 support-value | grep -E '^#|_LOG_)

To disable logging use a local definition file and set
`_M_GLOBAL_LOG_LVL=0`

    $ cat script0.def
    _M_GLOBAL_LOG_DST=$PWD/$prog.log
    _M_GLOBAL_LOG_LVL=0

To enable logging to standard error, set `_M_GLOBAL_LOG_LVL=1`

To enable logging to the file, set `_M_GLOBAL_LOG_LVL=2`.

Lines to be sent to the logger use a dedicated file descriptor, which is
`7`

Here is a test function to be used for those different configurations.

    d_log0 () {
      echo $FUNCNAME standard output >& 1
      echo $FUNCNAME standard error >& 2
      echo $FUNCNAME logger >& 7
    }

It is also possible to specify the destination for logging with the
command-line option: `--log-dest=t.log`. This also sets the
`_M_GLOBAL_LOG_LVL` value.

## Network Logging and `syslog-ng`

To send logging messages to a network destination, you can use `socat`
on a TCP or TCP6 socket. When used in this way, the log messages will
contain the RFC 3164 control information. This method does not need root
privileges.

When used with `syslog-ng`, it is safer to run `syslog-ng` from a user
account and use `setcap` to allow unprivileged users to run it.

    /usr/bin/sudo /usr/sbin/setcap cap_net_bind_service=ep /usr/sbin/syslog-ng

In a user systemd unit, this is a useful invocation

    ExecStart=/usr/sbin/syslog-ng ${X_ARGS} \
        --foreground \
        --cfgfile=%E/syslog-trace/syslog-trace.conf \
        --pidfile=%t/syslog-trace.pid \
        --control=%t/syslog-trace.ctl \
        -R %S/syslog-trace.persist

And this is a simple configuration for `syslog-ng`. You will need to
define the domain names `local0.6site0` and `local0.site0` or not use
them at all and remove them from the configuration.

You will need to change the UID of 1000 to your own.

The multicast network is mcast://239.255.0.2:17777

## Special Logging Levels

By default, the logging is to the facility `local0` and at `debug`
level.

If you need to change this, there is a function `d_alert`

    d_alert 2 the message to display

The number \"2\" will raise at \"critical\".

Another way to raise a syslog message at a different level is to use
this format

    printf "<138> [%s] level\n" "$FUNCNAME:$e_cmd" >&7

This send a logging line to the logging file descriptor. The number 138
can be calculated in

`PRI = (Facility × 8) + Severity`

# USER LOADER SCRIPTS - USER AND MACHINE EXTENSIONS

User-loader scripts are those that load their script libraries and
definitions from the same directory that the loader-script is in.

This provides an extra feature. If the `-m` option is given on the
command-line it will load additional script libraries from the
sub-directory named by the *machine* parameter to `-m machine` by
default it is the current host.

On a machine called `kaya`, the audit-function reports this library file
and definitions:

    $ script0 this0 support
    /misc/sistemoj/prj-public/src/m2_/demo/script0.sh
    weaves:devel@kaya:.../src/m2_/demo
    $ script0 this0 support-def
    /srv/nfs4/sistemoj/site/etc/m2_.def
    /srv/nfs4/sistemoj/site/share/site/cluster/m2_.def
    /srv/nfs4/sistemoj/site/share/site/kaya/m2_.def
    /misc/sistemoj/prj-public/src/m2_/demo/script0.def

The script is being run from the directory:
`/misc/sistemoj/prj-public/src/m2_/demo` and it finds the `script0.sh`
library file.

For the definitions, it finds the loader-implementation\'s definition
files; m2\_.def and finally the script0.def file.

They are loaded in that order and that feature was used to **not** use
the default log destination in the earlier discussion of logging.

On a machine called `maria`, the same commands use an existing
sub-directory for *maria* to load extra scripts and definitions.

    $ script0 this0 support
    /misc/sistemoj/prj-public/src/m2_/demo/script0.sh
    /misc/sistemoj/prj-public/src/m2_/demo/maria/script0.sh
    $ script0 this0 support-def
    /srv/nfs4/sistemoj/site/etc/m2_.def
    /srv/nfs4/sistemoj/site/share/site/cluster/m2_.def
    /misc/sistemoj/prj-public/src/m2_/demo/script0.def
    /misc/sistemoj/prj-public/src/m2_/demo/maria/script0.def

The *machine* can be given explicitly with `-m maria` when run on the
machine kaya.

The `-m maria` sets the variable `d_machine` this can also be set in the
shell environment when the script-loader is run.

The *machine* variant need not of course be a machine. It could be any
variant you might want to load. For example, `-m strongswan` would
search a sub-directory strongswan/ for a file script0.sh and load that.
This script-library might contain additional code to manage StrongSWAN
VPN connections.

The `-u user` command-line option can be used in the same way as the
`-m` machine option. It will load after the *machine* script-library.

You may also have noticed other differences between the kaya and maria
audit-function reports for support-def. kaya also loads
`/srv/nfs4/sistemoj/site/share/site/kaya/m2_.def`. There is a feature of
the audit-function to see what the load path is:
`script0 this0 mloader`.

# CODE-LEVEL LOADING

Another feature of a loader-script is the cl-loader (code-level loader).
This makes it possible to load functions from other library-script. It
can be invoked at code-level using the loader-implementation function
`d_resolve1`. It is also invoked on the initial load of a loader-script.
To understand how it could work, this illustrates it not working in the
initial load.

Using the demonstration loader-script, try and load a function that
doesn\'t exist because we have misspelled the name. Here stating `tihs0`
and not `this0`

    $ script0 tihs0 support

    !!! ERROR REPORT !!!
    [d_resolve1] (Error 4): Library file [script0.sh] not found in /usr/local/etc/m_loadr.
    !!!!!!!!!!!!!!!!!!!!

The error tells us that a library file could not be found in the
directory `/usr/local/etc/m_loadr`.

That directory is specified by the environment variable `_M__LOADR_`,
which can be seen with `script0 this0 support-value`

    # /srv/nfs4/sistemoj/site/etc/m2_.def
    _M__LOADR_=/usr/local/etc/m_loadr

On this system, the `/usr/local/etc/m_loadr` directory contains two
files:

    $ ls /usr/local/etc/m_loadr
    m2_.sh  m_.sh

`m_` is the library script for library scripts. It contains nearly a
hundred functions that can be used.

If I try to find the badly named function in that:

    $ m_ tihs0 support

    !!! ERROR REPORT !!!
    [d_resolve1] (Error 8): Extraction failed. Function [d_tihs0] not in [m_.sh].
    !!!!!!!!!!!!!!!!!!!!

The `d_resolve1` function now reports a different error, it failed to
find the function in the library-script in
`/usr/local/etc/m_loadr/m_.sh`

The demonstration `script0.sh` library-script contains this call
`d_resolve1 d_ls m_`. This loads the function `d_ls` from the
library-script `m_.sh` in the *m\~loadr\~* directory.

If we pre-load `d_ls` and have a function in our user-form script
script0.sh that uses it:


    # the pre-load can be made when the library-script is loaded
    # d_resolve1 d_ls m_

    d_ls1 () {
      local e_cmd=$1
      shift

      # or the pre-load can be made when the function is used.
      d_resolve1 d_ls m_

      case $e_cmd in
        inode-idx)
          find ${d_dir:-$PWD} -type f -printf "%i %p\n"
          ;;

        undot) # calling d_ls directly
          d_ls undot $*
          ;;
        *) # using d_ls as a fall-through.
          d_ls $e_cmd $*
          ;;
      esac
    }

So the function `d_ls1` not supports `m_ ls undot` by a named
pass-through and supports `mergerfs` by the unnamed fall-through.

    $ find . -type f | script0 ls1 undot
    script0.sh
    maria/script0.sh
    maria/script0.def
    demo.log
    script0.def
    work.log
    script0.err
    make.log
    numbers.lst
    bill/script0.sh
    t.log
    $ script0 ls1 mergerfs /media/tv-0/Youth\ \(2026\)\ \[tvdbid-470000\]/
    getfattr: Removing leading '/' from absolute path names
    # file: media/tv-0/Youth (2026) [tvdbid-470000]/
    user.mergerfs.allpaths="/a/l/RA-media/share/tv0/Youth (2026) [tvdbid-470000]\000/a/l/SI-media/share/tv0/Youth (2026) [tvdbid-470000]\000/a/l/SM-media/share/tv0/Youth (2026) [tvdbid-470000]"

In this way, loader-scripts need not include a whole library-script
using the BASH `source` directive. It can selectively include just one
function.

The pre-load function `d_resolve1` takes two parameters: the function to
load and the filename (not the path) of the library-script in the
`/usr/local/etc/m_loadr/m_.sh`.

# ORCHESTRATE - SEQUENCED OPERATIONS

The demo loader-script also illustrates the `--orchestrate` command-line
option. This allows a sequence of operations to be executed. It is most
often used to generate files.

    d_resolve1 f_orchestrate m2_
    d_resolve1 e_orchestrate m2_

    e_fragments0=""

    d_fragments0 () {
      local cmd="${1:-}"

      case $cmd in
      header0)
        e_fragments0="${cmd}-$RANDOM"
        ;;
      body0)
        e_fragments0=" $e_fragments0 ${cmd}-$RANDOM"
        ;;
      footer0)
        e_fragments0=" $e_fragments0 ${cmd}-$RANDOM"
        ;;
      print0)
        echo $e_fragments0
        ;;
      esac

    }

    d_example1 () {
      e_orchestrate d_fragments0
    }

The two functions `e_orchestrate` and `f_orchestrate` are pre-loaded. A
generator function: `d_fragments0` has been implemented supporting
sub-commands. The `--orchestrate=arg` is specified as a sequence of
sub-commands separated by a comma, `,`.

The co-ordinating function `d_example1` is used to invoke
`e_orchestrate` using `d_fragments0`. The `--orchestrate=<sequence>` is
then processed by the `d_example1` call to `e_orchestrate`.

    $ script0 --orchestrate=header0,body0,footer0,print0 example1
    header0-30431 body0-17640 footer0-1844

And other sequences can be given:

    $ script0 --orchestrate=header0,body0,body0,body0,footer0,print0 example1
    header0-2288 body0-15399 body0-7306 body0-6741 footer0-6311

Notice that because all the function calls that `e_orchestrate` are
within the same process, the shell variable used to collate the result,
`e_fragments0` can accumulate.

This should work across sub-shells: so a new sub-command added to
`d_fragments0`

    body1)
      e_fragments0=$(echo $e_fragments0 ${cmd}-$RANDOM)"
      ;;

would do the same as the `body0` sub-command.

If the `e_fragments0` is exported, it can be operated upon directly by
the sub-shell.

About naming of functions: `d_fragments0` has been given the `d_` prefix
so that one can test the separate sub-commands directly from the
command-line: `script0 fragments0 body0` for example.

The function could have any name when it is called by `e_orchestrate`.

# ADDING SHELL VARIABLES - EVLR

There is a function provided by the loader-implementation `d_evlr` which
will set shell variables. The string to process is of the form
`a=b,c=d`. Given this string, `d_evlr` will set the shell a and b as
shell variables with the values \"b\" and \"d\".

This use of `d_evlr` has been made available on the command-line options
using two options: `-o arg` and `-e arg`.

In the demonstration script, `d_xoptions` illustrates this:

    $ script0 -othis=that xoptions
    this=that

    this : "that"

The option `-e arg` does exactly the same, but is expected to be used
for programs. `d_xoptions` also demonstrates the shell variable are set
by the `-e arg`

    $ script0 -ethis=that -othese=those xoptions
    these=those
    this=that
    this : "that"

The `-e arg` is usually used to select a function to be used within a
function. The function `d_exec0` illustrates this.

    $ script0 exec0
    cat
    1
    2
    3
    4
    5
    $ script0 -e 'wc -l' exec0
    wc -l
    5

The default the `-e arg` is cat. In the second invocation, `wc -l` is
passed.

## Temporary Files - `e_tpush1`

Temporary files can be managed by the loader-script using the
loader-implementation method `e_tpush1`

To get a temporary file, create a local variable to contain the path
generated for a temporary file and pass that variable name to the
function `e_tpush1`. The variable name is used as a local name-ref.

    local tfile
    e_tpush1 "tfile"

The function is called `e_tpush1` because it uses a stack to hold the
temporary file names. These are then deleted when the loader-script
exits.

## Paths

`e_path_parse` is a function that parses a path and returns it as an
array

Invoked like this `local -a path0; e_path_parse /tmp/t.out "path0"`. It
only uses BASH variable substitutions.

This is the array for a path (left column) and a URI (right column)

  --- ----------- --------------------------
  0   Directory   Hostname/IP
  1   Basename    Full address (host port)
  2   Extension   Scheme (tcp socket http)
  3   Filebase    Base path
  4   Depth       Depth of base path
  5   \-          Port
  --- ----------- --------------------------

It must contain `://` to be considered as a URI. Here are some examples:
First a path, and then some URIs.

    $ script0 path0 $PWD/script0.sh
    declare -a path0=([0]="/misc/sistemoj/prj-public/src/m2_/demo" [1]="script0.sh" [2]="sh" [3]="script0" [4]="6" [5]="")
    $ script0 path0 http://polly.6site0:9091/transmission
    declare -a path0=([0]="polly.6site0" [1]="polly.6site0:9091/transmission" [2]="http" [3]="/transmission" [4]="13" [5]="9091")
    $ script0 path0 mcast://238.255.0.2:17777
    declare -a path0=([0]="238.255.0.2" [1]="238.255.0.2:17777" [2]="mcast" [3]="" [4]="0" [5]="17777")
    $ script0 path0 file://$PWD/script0.sh

# CODE SAFETY ERROR TRAPS AND TRACING

The loader-implementation implements the **no unset variable**
requirement for BASH, that is `set -o nounset` or simply `set -u`. This
means that an unset variable cannot be used.

    $ script0 path0 
    /misc/sistemoj/prj-public/src/m2_/demo/script0.sh: line 357: 1: unbound variable

    !!! ERROR REPORT !!!
    [script0] Unknown failure in d_path0 (Status: -1)
    !!!!!!!!!!!!!!!!!!!!

The error message above also illustrates that a line number is given
with an error. This is an addition to BASH and can help track down
mistakes in large scripts.

The code that caused the error is this:

    d_path0 () {
      local -a path0=()
      e_path_parse "${1}" path0
      declare -p path0
    }

It\'s fairly simple assign an empty string as default with: `"${1:-}"`,
but this might pass the problem onto the function. If you want to handle
the error and not return the `255` or `-1` error level, then
`test -n "${1:-}" || return 1`. You can also set the error message to be
used: `test -n "${1:-}" || { d_ERRMSG`\"a path or URI is required\";
return 1; }=

The error handling is dealt with my BASH traps. Because of that, it\'s
recommended that you exit functions using `return` rather than `exit`.
When a function returns, it goes back to the caller which has some
additional processing it can perform.

To trace the execution of the library-script, use the `-x` flag. This
avoids tracing the start-up and loading code of the
loader-implementation. You will see trace from the
loader-implementation\'s library-script if you use any of the utility
methods.

If you need to develop the loader-implementation, you can use the system
trace variable: `: ${_M__TRACE_:`\"-\"}= is its default value, ie. `-`
do nothing.

Values can be assigned: `d, n, p` are the values, several can be set
together.

d

:   debug, ie. trace the loader-implementation code and the
    library-script.

n

:   nodo, ie. set the shell variable `nodo` to the value `echo`, usually
    it is an empty string.

p

:   no-nounset, do not activate the `set -o unset` feature, so that
    unset variables can be used.

# COMMAND EXECUTION ENVIRONMENT

The environment is as the calling shell. The environment has only
`set -o` nounset. Many of the loader-implementation utilities have been
implemented, or have alternative implementations, that use local
name-refs to pass parameters and return values via these.

These features are only available in later versions of BASH, in
particular, version 5.2.

The loader-implementation may have made assumptions about shared
environment and file-descriptors. This will only be an issue with
different forms of function invocations, when the function is defined in
the same library-script, either directly stated or when loaded by
`d_resolve1` or equivalently by means of BASH `source file`.

These invocations have been improved in BASH 5.2 to take place in the
same process space and will share its environment and file descriptors.
In these examples, the `d_function` could be any shell function.

`$(d_function)`

:   usually in this way `local val=$(d_function)`.

`<(d_function)`

:   usually used for piping input:
    `while read i; do echo $i; done < <(d_function)`

`<<< $(d_function)`

:   usually used like this:
    `while read i; do echo $i; done < <<< $(d_function)`

# EXIT STATUS

The exit status is usually the return value of the last executed
command; this can be overridden by explicitly stating `return 0` or some
other value. You may choose to return `-1`, this will trigger the `ERR`
and report the line number.

If a syntax error or some other BASH parsing error (unbalanced
delimiters, for example), then the exit value will be `-1`.

Rarely, other errors will be generated, `pipefail` may arise within the
logging component.
